## Суть продукта

**Рефлекс** — ИИ-диспетчерская рядом с системами сервисной компании «СеверХолод», не внутри их CRM. Диспетчер (или e2e) подаёт свободный текст обращения. Модуль извлекает факты, сверяется со справочниками, применяет регламент и либо готовит создание/обновление заявки, либо останавливается: уточнение, очередь диспетчера, согласование.

Это не замена ITSM, не омниканальный ящик и не бот, который сам пишет клиенту.

Пилот — два контура: мок систем СеверХолода и сам Рефлекс. Сначала поднимаем мок, потом Рефлекс.

---

## Для кого

- **Диспетчер** — единственная роль в пилоте. Создаёт обращение, смотрит стол и журнал, читает карточку, дописывает факт в диалог. Клиент СеверХолода в UI не работает.

---

## Какую задачу решает

Сейчас диспетчер сам ищет клиента, объект, оборудование, договор и открытые заявки. На одно входящее уходит около 12 минут. Ошибки в площадке, активе и приоритете дают повторные обращения и срыв SLA. Рефлекс проводит ту же цепочку на виду: факты, ответы систем, исход, dry-run заявки, черновик ответа.

---

## Что в первой очереди (MVP)

- Мок СеверХолода: поиск площадок, активов, договора, открытых заявок; create/update заявки в dry-run.
- Рефлекс: вход диспетчера, стол, журнал, форма обращения, карточка с чатом.
- Один агент разбора, пять тулов, стрим на карточке, Langfuse.
- Четыре приёмочных кейса S1–S4.

---

## Критерий успеха MVP

Свободный текст → видимые факты и tool calls → одно понятное решение → dry-run заявки или честный останов, без угадывания площадки.

---

## Примеры запросов / действий пользователя

- Войти и открыть стол с четырьмя корзинами статусов.
- Создать обращение по сценарию «ХУ-18 на Дмитровском» и дождаться карточки с create + would-id.
- Открыть неоднозначную «17-ю» и увидеть два кандидата, не одну выбранную Москву.
- На карточке повторного звонка увидеть update T-884, не новую заявку.
- Дописать в диалог «это Дмитровское» и получить пересчёт на том же обращении.
- Открыть журнал, отфильтровать «нужно уточнение», кликнуть строку.

---

## Не является

- Заменой CRM / EAM / ITSM.
- Коннектором почты, Telegram, телефонии, личного кабинета.
- Очередью входящих и склейкой переписки.
- Исходящей отправкой клиенту.
- Semantic RAG и обучением своей модели.
- Кнопкой «агент был неправ».
- Production-контуром с SSO, ролями и живой записью в заявки (по умолчанию).

## Ограничения прототипа (сами себе)

Бриф это не запретил и не описал — фиксируем как условие пилота, не как долг.

| Тема | Как в прототипе |
|------|-----------------|
| Пользователи | Один логин/пароль в конфиге. Нет SSO, LDAP, ролей, аудита доступа |
| Сессия | Cookie сессии. Назад после выхода на стол не пускает |
| Стоп прогона | Нет кнопки Stop / cancel |
| Вложения | Только второе текстовое поле, не файлы |
| Журнал | Без пагинации, выгрузки, массовых действий |
| Назначение группы | Нет справочника групп — не назначаем |
| Контакты CRM | Нет. «Андрей» — не сущность |
| Мок | Отдельный сервис, сид из JSON. Своей БД нет. В интернет не ходит |
| Рефлекс storage | PostgreSQL: обращения, лента, хронология. Справочники объекта сюда не копируем |
| Тема UI | Тёмная по умолчанию, переключатель светлая/тёмная |
| Запись заявок | Dry-run по умолчанию. Живой CRUD — только явный флаг мока |
| Модель в UI | Диспетчер модель и конфиг агента не выбирает |
| Язык UI и промпта | Русский |
