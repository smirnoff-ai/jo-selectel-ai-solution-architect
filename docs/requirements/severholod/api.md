# API систем СеверХолода (пилот)

**Заказчик:** ООО «СеверХолод»  
**Статус:** принят.  
**Дата:** 24 августа 2026.

Здесь только то, что **мы отдаём** модулю Рефлекс: поиск по справочникам и работа с заявками. Inbox, почта, Telegram и исходящие в канал в этом контуре не существуют. Метод «принять обращение» — сторона Рефлекса, в этот файл не входит.

Базовый URL мока локально: `http://mock-severholod:8080`. Протокол HTTP, JSON, UTF-8.

---

## Общие правила

Пустой поиск — `200` и `"items": []`, не `404`. Несколько совпадений — тоже `200` и все элементы: мок не выбирает «наиболее вероятное». Ресурс по точному id, которого нет, — `404`. Невалидное тело или провал ФЛК на write — `400` с списком проверок. Неверная схема JSON — `422`.

Формат ошибки:

```json
{
  "detail": "Человекочитаемое описание",
  "code": "not_found",
  "checks": []
}
```

Поле `checks` заполняем только на ФЛК заявки. Коды: `not_found`, `validation`, `flk_failed`.

Служебное: `GET /health` → `200` и `{"status": "ok"}`. Отдельных «часов компании» в API нет. В брифе есть `current_time` сида — это дата мира демо, не метод. Рефлекс считает SLA от времени получения обращения, которое пришло во входе, а не спрашивает мок «который час».

## 1. Клиенты и объекты

`GET /crm/v1/sites`

Ищет площадку и клиента. Закрывает tool `find_customer_or_site`. Один только `q` был бы неудобен: агент уже знает `customer_id` или `site_id` после первого попадания и должен сужать точно, а не снова искать подстрокой. Поэтому конкретные поля — отдельные опциональные фильтры. Свободная строка `q` остаётся для первого прохода по тексту письма.

| Параметр | Обязателен | Смысл |
|----------|:----------:|--------|
| `q` | нет | Подстрока без регистра сразу по имени клиента, адресу и id |
| `customer_id` | нет | Точное равенство, например `C-101` |
| `site_id` | нет | Точное равенство, например `S-MSK-01` |
| `customer_name` | нет | Подстрока без регистра по имени клиента |
| `address` | нет | Подстрока без регистра по адресу |
| `timezone` | нет | Точное равенство (`Europe/Moscow`, `Asia/Yekaterinburg`) |

Нужен хотя бы один параметр. Ни одного — `422`. Несколько конкретных фильтров складываются через И. Если рядом есть `q`, он дополнительно сужает уже отобранное (тоже И): `customer_id=C-101&q=Дмитровское` даёт только `S-MSK-01`, а не обе площадки СеверФуда.

Контактов в CRM нет. «Андрей» из письма — факт на обращении Рефлекса, не поле площадки. Поиск `q=Андрей` ничего не находит.

Примеры: `GET /crm/v1/sites?q=СеверФуд`, `GET /crm/v1/sites?address=Дмитровское`, `GET /crm/v1/sites?customer_id=C-101`, `GET /crm/v1/sites?site_id=S-MSK-01`.

Успех, несколько площадок одного клиента:

```json
{
  "items": [
    {
      "site_id": "S-MSK-01",
      "customer_id": "C-101",
      "customer_name": "СеверФуд",
      "address": "Москва, Дмитровское шоссе, 100",
      "timezone": "Europe/Moscow"
    },
    {
      "site_id": "S-EKB-02",
      "customer_id": "C-101",
      "customer_name": "СеверФуд",
      "address": "Екатеринбург, улица Монтажников, 7",
      "timezone": "Asia/Yekaterinburg"
    }
  ]
}
```

Одно совпадение по адресу (`address=Дмитровское` или `q=Дмитровское`) — в `items` только `S-MSK-01`.  
Точный `site_id=S-MSK-01` — один элемент, даже если имя клиента общее.  
Пустой поиск (`q=НеизвестнаяФирма`) — `"items": []`.  
Ни одного параметра — `422`.

`GET /crm/v1/sites/{site_id}` — карточка одной площадки теми же полями, без обёртки `items`. Нет id — `404`.

## 2. Реестр оборудования

`GET /eam/v1/assets`

Закрывает `find_assets`.

| Параметр | Обязателен | Смысл |
|----------|:----------:|--------|
| `q` | нет | Подстрока без регистра сразу по локальному коду, `asset_id` и типу |
| `asset_id` | нет | Точное равенство, например `A-1001` |
| `site_id` | нет | Точное равенство площадки |
| `local_code` | нет | Подстрока или точное равенство кода («ХУ-17», «КМ-4») |
| `asset_type` | нет | Подстрока по типу («холодильная установка», «компрессор») |
| `criticality` | нет | Точное равенство: `high` или `medium` |

Нужен хотя бы один параметр. Ни одного — `422`. Несколько конкретных фильтров складываются через И. Если рядом есть `q`, он дополнительно сужает уже отобранное.

Запрос `GET /eam/v1/assets?local_code=ХУ-17` или `q=ХУ-17` без площадки обязан вернуть **оба** актива: московский и екатеринбургский. Мок не предпочитает тот, где уже есть открытая заявка. `local_code=ХУ-17&site_id=S-MSK-01` — только `A-1001`.

```json
{
  "items": [
    {
      "asset_id": "A-1001",
      "site_id": "S-MSK-01",
      "local_code": "ХУ-17",
      "asset_type": "холодильная установка",
      "criticality": "high"
    },
    {
      "asset_id": "A-1002",
      "site_id": "S-EKB-02",
      "local_code": "ХУ-17",
      "asset_type": "холодильная установка",
      "criticality": "high"
    }
  ]
}
```

`GET /eam/v1/assets?site_id=S-MSK-01&local_code=ХУ-18` — один элемент `A-1003`, `criticality` = `medium`.  
`GET /eam/v1/assets?site_id=S-MSK-03` — список активов площадки, в сиде это `A-2001` (КМ-4).  
`GET /eam/v1/assets?asset_id=A-2001` — тот же КМ-4 без обхода площадки.  
`GET /eam/v1/assets?criticality=high` — оба ХУ-17, без ХУ-18 и КМ-4.  
Неизвестный `site_id` — `200` и пустой список, не `404`: площадку проверяет CRM, реестр просто ничего не нашёл.

`GET /eam/v1/assets/{asset_id}` — один актив. Нет — `404`.

`criticality` в сиде: `high` или `medium`. Других значений мок не отдаёт.

## 3. Договоры

`GET /contracts/v1/contracts?site_id=S-MSK-01`

Закрывает `get_contract`. Параметр `site_id` обязателен.

В сиде на площадку один действующий договор. Несколько договоров на одну площадку пилот не моделирует: либо один элемент, либо пустой список.

```json
{
  "items": [
    {
      "contract_id": "K-101",
      "site_id": "S-MSK-01",
      "plan": "Gold",
      "response_sla": "60_minutes",
      "service_window": "24x7",
      "coverage": ["diagnostics", "repair", "spare_parts_up_to_50000_rub"]
    }
  ]
}
```

Нормализация относительно текста задания: `response_sla` отдаём кодом, не свободной английской фразой.

| Код `response_sla` | Смысл |
|--------------------|--------|
| `60_minutes` | 60 минут от момента получения, окно 24×7 (Gold, K-101) |
| `4_business_hours` | 4 рабочих часа в окне договора (Standard, K-102) |
| `next_business_day` | следующий рабочий день в окне договора (Basic, K-203) |

| Код `service_window` | Смысл |
|----------------------|--------|
| `24x7` | без календарных исключений |
| `weekdays_09_18_local` | пн–пт, 09:00–18:00 в `timezone` площадки |

`coverage` — массив кодов: `diagnostics`, `repair`, `spare_parts_up_to_50000_rub`. Basic (K-203) содержит только `diagnostics`.

`GET /contracts/v1/contracts/{contract_id}` — один договор. Нет — `404`.

Рефлекс не просит мок посчитать дедлайн. Мок отдаёт сырые коды; формулы — в регламенте, когда до него дойдём.

## 4. Заявки: чтение

`GET /itsm/v1/tickets`

Закрывает `find_open_tickets`.

| Параметр | Обязателен | Смысл |
|----------|:----------:|--------|
| `customer_id` | нет | Клиент |
| `site_id` | нет | Площадка |
| `asset_id` | нет | Актив |
| `contract_id` | нет | Договор, на который повешена заявка |
| `status` | нет | Один статус или `open` — все незакрытые |

Хотя бы один фильтр из `customer_id`, `site_id`, `asset_id`, `contract_id` обязателен. Иначе `422`.

### Справочник статусов заявки

В брифе у единственного тикета T-884 был только статус `waiting_for_customer`. Для dry-run create/update и для фильтра `status=open` этого мало: нужно явно сказать, какие статусы считаем живой заявкой (её можно дополнять), а какие — закрытой историей (автоматом не обновляем, это уже новое дело). Ниже — наш пилотный справочник, не статусы настоящей ITSM СеверХолода. Других значений мок не принимает и не отдаёт.

| Код | Группа | Когда ставится | Что можно делать |
|-----|--------|----------------|------------------|
| `new` | открытый | Только что созданная заявка, группа ещё не взяла в работу. В dry-run create мок отвечает `would_status: new`. | Искать как открытую, обновлять текст и приоритет |
| `in_progress` | открытый | Сервисная группа уже ведёт работы. В сиде таких нет, код нужен, чтобы фильтр `open` и ФЛК не сломались на втором статусе «ещё жива». | Искать как открытую, обновлять |
| `waiting_for_customer` | открытый | Ждём ответа или доступа с объекта. Так в сиде стоит T-884: диспетчер уже заводил заявку, клиент пишет снова. | Искать как открытую, обновлять (сценарий «повтор») |
| `closed` | закрытый | Работы закончены, заявку закрыли штатно. В сиде нет. | В `status=open` не попадает. PATCH в dry-run падает на `ticket_is_open` |
| `cancelled` | закрытый | Заявку сняли, не выполняя. В сиде нет. | Как `closed`: не открытая, авто-update нельзя |

Фильтр `status=open` — это три открытых кода сразу, не отдельный статус в карточке. `status=waiting_for_customer` — ровно один код. Закрытую заявку можно найти только явным `status=closed` или `status=cancelled`, либо запросом по id.

Для регламента Рефлекса достаточно такого правила: тот же инцидент и статус из открытой группы — сразу update; тот же актив, но заявка закрыта — не оживлять, это кандидат на новую заявку. Сид содержит одну открытую:

```json
{
  "items": [
    {
      "ticket_id": "T-884",
      "customer_id": "C-101",
      "site_id": "S-MSK-01",
      "asset_id": "A-1001",
      "contract_id": "K-101",
      "status": "waiting_for_customer",
      "priority": "high",
      "summary": "Температура +7, возможная неисправность компрессора",
      "created_at": "2026-08-13T15:55:00+03:00",
      "updated_at": "2026-08-13T15:55:00+03:00"
    }
  ]
}
```

`customer_id`, `site_id` и `contract_id` в ответе добавлены явно: в тексте задания у тикета был только `asset_id`. Заявка должна быть привязана к договору, а не каждый раз заново «угадывать» его по площадке. Сейчас в сиде на площадку один договор, поэтому T-884 → K-101 однозначно. Поле всё равно храним на тикете: покрытие и SLA на момент открытия не должны поехать, если договор площадки потом сменят. Это допущение сида, не выдуманный второй тикет.

`GET /itsm/v1/tickets/T-884` — та же карточка без `items`. Нет id — `404`.  
`GET /itsm/v1/tickets?asset_id=A-1003` — пустой список: открытой заявки на ХУ-18 нет.

## 5. Заявки: создание и обновление

Поля `dry_run` в запросе нет. Настоящая ITSM СеверХолода такого флага не имеет: заявка либо создаётся, либо нет. В пилоте режим задаёт **конфиг мока**, не Рефлекс в каждом вызове.

По умолчанию мутации выключены (`ALLOW_TICKET_MUTATIONS=false`). `POST` и `PATCH` только гоняют ФЛК, пишут лог и отвечают, какую заявку приняли бы. Реестр открытых тикетов не меняется, в ответе `persisted: false` и `would_ticket_id`. Если мутации в конфиге включить — те же методы пишут по-настоящему, в ответе `persisted: true` и обычный `ticket_id`.

### Создать

`POST /itsm/v1/tickets`

```json
{
  "customer_id": "C-101",
  "site_id": "S-MSK-01",
  "asset_id": "A-1003",
  "contract_id": "K-101",
  "summary": "ХУ-18 не запускается после перезагрузки",
  "priority": "high"
}
```

| Поле | Обязательно | Смысл |
|------|:-----------:|--------|
| `customer_id` | да | Клиент из CRM |
| `site_id` | да | Площадка из CRM |
| `asset_id` | нет | Если есть — должен принадлежать `site_id` |
| `contract_id` | да | Договор площадки; ФЛК сверяет, что он существует и его `site_id` совпадает |
| `summary` | да | Текст, не пустой |
| `priority` | да | `low` / `medium` / `high` / `critical` |

Вида работ (`requested_action`, диагностика / ремонт / запчасти) на заявке нет. В сиде у T-884 такого поля не было. Покрытие договора Рефлекс смотрит сам и решает, можно ли автоматом заводить заявку; ITSM принимает идентичность, текст и приоритет. Справочник действий, если понадобится, живёт в регламенте, не здесь.

Успешная проверка без записи (пример для ХУ-18, id из сида заявок нет — мок резервирует следующий):

```json
{
  "persisted": false,
  "accepted": true,
  "would_ticket_id": "T-885",
  "would_status": "new",
  "payload": {
    "customer_id": "C-101",
    "site_id": "S-MSK-01",
    "asset_id": "A-1003",
    "contract_id": "K-101",
    "summary": "ХУ-18 не запускается после перезагрузки",
    "priority": "high"
  },
  "checks": [
    {"id": "customer_exists", "passed": true},
    {"id": "site_exists", "passed": true},
    {"id": "site_belongs_to_customer", "passed": true},
    {"id": "asset_belongs_to_site", "passed": true},
    {"id": "contract_exists", "passed": true},
    {"id": "contract_belongs_to_site", "passed": true},
    {"id": "summary_present", "passed": true},
    {"id": "priority_known", "passed": true}
  ]
}
```

`would_ticket_id` при выключенных мутациях стабилен для одинакового payload в рамках сессии мока, чтобы карточку можно было показать повторно. В реестр он не попадает: второй поиск открытых T-885 не увидит.

### Обновить

`PATCH /itsm/v1/tickets/{ticket_id}`

```json
{
  "summary": "Температура 8,3. Резервная камера есть, нагрузка под вопросом",
  "priority": "high"
}
```

Менять можно `summary`, `priority`, `status` (только внутри открытых). Нельзя сменить `customer_id`, `site_id`, `asset_id`, `contract_id` этим методом.

Поля назначения на сервисную группу нет. В брифе диспетчер «передаёт заявку нужной группе», но в сиде нет справочника групп. Свободную строку без справочника не заводим: Рефлекс в пилоте не назначает бригаду через этот API. Если группа понадобится — сначала каталог, потом поле.

Дополнительно к проверкам создания мок смотрит:

| id проверки | Условие |
|-------------|---------|
| `ticket_exists` | Тикет есть |
| `ticket_is_open` | Статус не `closed` и не `cancelled` |
| `identity_not_changed` | В теле нет чужих id клиента, площадки, актива или договора |

Провал любой проверки — `400`, `accepted: false`, в `checks` все пункты с `passed`. Пример: обновление несуществующего id.

```json
{
  "persisted": false,
  "accepted": false,
  "would_ticket_id": null,
  "would_status": null,
  "payload": {},
  "checks": [
    {"id": "ticket_exists", "passed": false, "detail": "T-999 not found"}
  ]
}
```

## 6. Чего в этом API нет

Нет списка входящих, ack писем, отправки клиенту, склада, биллинга, геокодера. Нет вида работ на заявке и нет проверки покрытия: договор отдаём как справочник, решение «ремонт по Basic нельзя» — у Рефлекса. Нет расчёта SLA: мы отдаём коды договора и критичность актива. Нет выбора «лучшей» площадки из двух ХУ-17.

Сид пилота — данные раздела 4 селектловского брифа плюс явные допущения выше: на T-884 поля клиента, площадки и договора K-101; коды SLA и окна вместо английских фраз. Контактов в CRM нет.
