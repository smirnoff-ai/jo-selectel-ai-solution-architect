# Датасет приёмки разбора

**Заказчик:** ООО «СеверХолод»  
**Дата:** 25 августа 2026  
**Статус:** черновик на четыре кейса, один прогон каждый. Автотест (AgentEval) и ручной прогон читают одни и те же ожидания.

Справочники — сид из [api.md](api.md), без дописывания тикетов. Время мира демо: `2026-08-13T16:40:00+03:00`. Формулы приоритета в [regulations.md](regulations.md) ещё нет: в кейсах фиксируем то, что уже можно проверить без арифметики. Точное `priority.value` не валит кейс, пока регламент не принят.

Второй прогон (реплика диспетчера на том же обращении) в этот набор не входит.

---

## Как устроен кейс

Каждый кейс — одно новое обращение. Поля входа совпадают с формой. После одного прогона агента смотрим карточку и факт примерки, не красоту markdown.

**Жёстко** (автотест и ручной чеклист): канал и текст входа; какие поиски обязаны быть (не порядок); `binding.status` и id либо список кандидатов; исход из набора `create` / `update` / `clarify` / `dispatch` / `approve` / `refuse_auto`; была ли примерка ITSM; `auto_in_prod`.

**Мягко** (глазами, в AgentEval — не блокер): формулировка `reason`, текст вопросов, черновик ответа, какие именно цитаты в `evidences`. Порядок тулов не фиксируем.

**Почему так** — абзац правилом. Без него цифра «ожидаем clarify» бесполезна, когда правило сменят.

Для AgentEval позже: один кейс = один прогон, assert по полям ниже, трасса в Langfuse с `appeal_id` и тегом `scenario_id`.

## S1. Полный запрос (бриф, сценарий 1)

Нужен счастливый путь: опора однозначна, открытого тикета на ХУ-18 нет, автоматика должна дойти до create и примерки.

**Вход**

| Поле | Значение |
|------|----------|
| Канал | email |
| Отправитель | не указан |
| Получено | 2026-08-13T16:40:00+03:00 |
| Текст | СеверФуд, склад на Дмитровском шоссе, 100. ХУ-18 не запускается после перезагрузки. Продукцию пока перенесли в соседнюю камеру. Нужен выезд специалиста. |
| Вложение | нет |

**Поиски.** Должны вызваться поиск площадок (СеверФуд / Дмитровское) и поиск актива ХУ-18. Договор площадки — да, объект станет одним. Открытые заявки — да, чтобы не пропустить тикет; на A-1003 пусто.

**Карточка**

| Слот | Ожидание |
|------|----------|
| Клиент | mention про СеверФуд, `resolved` `C-101` |
| Объект | mention про Дмитровское, `resolved` `S-MSK-01` |
| Оборудование | mention ХУ-18, `resolved` `A-1003` |
| Проблема / симптомы | не запускается после перезагрузки |
| Резерв | перенесли в соседнюю камеру |
| История | пусто или без тикета |
| Договор | `resolved` `K-101`, Gold, `60_minutes`, `24x7` |

Расчёт: ветка `create`, SLA `60_minutes`, дедлайн `2026-08-13T17:40:00+03:00`, пояс Москвы. Аргументы: получено 16:40, окно 24×7. Приоритет не `low` (критичность ХУ-18 — `medium`); точное значение — после регламента.

Исход `create`. Примерка ITSM **да**: клиент C-101, площадка S-MSK-01, актив A-1003, договор K-101, непустой summary. `auto_in_prod` true, если ФЛК принял (`persisted` в пилоте всё равно false).

**Почему.** Клиент и объект однозначны, актив один, открытого тикета на него нет. Заявку «на площадку без актива» выдумывать не пришлось.

**Руками.** После прогона в «разобрано», на карточке create и would-id, в чате видны вызовы поиска.

## S2. Неоднозначная 17-я (бриф, сценарий 2)

Нужен останов без угадывания города. Текст как в сценарии 2, заголовки как в примере входа брифа: иначе в письме нет даже имени клиента.

**Вход**

| Поле | Значение |
|------|----------|
| Канал | email |
| Отправитель | Андрей, СеверФуд |
| Получено | 2026-08-13T16:40:00+03:00 |
| Текст | Снова 17-я: температура уже +8 и продолжает расти. Вчера мастер говорил, что если повторится, нужно менять компрессор. Резервная камера вроде работает. Нужен человек сегодня до 19:00. |
| Вложение | нет |

**Поиски.** Площадки по СеверФуд — две. Активы по ХУ-17 / «17-я» — A-1001 и A-1002. Договор можно не звать: объекта нет. Тикеты без площадки или актива не должны выбрать «тот, где уже T-884», как будто город известен.

**Карточка**

| Слот | Ожидание |
|------|----------|
| Клиент | mention СеверФуд (из отправителя), `resolved` `C-101` допустим: клиент один |
| Объект | не `resolved`. Либо `ambiguous` с `S-MSK-01` и `S-EKB-02`, либо ещё не привязан, но не Москва наугад |
| Оборудование | mention «17-я», `ambiguous`, кандидаты `A-1001` и `A-1002` |
| Симптомы | +8, растёт |
| Срок | сегодня до 19:00, сырой текст |
| Резерв | вроде работает |
| История | упоминание вчерашнего мастера, тикет не `resolved` |
| Договор | `empty` |

Расчёт `blocked` или условный, без одного дедлайна «как будто Дмитровское». Исход `clarify`. Вопросы не пустые (какой город / какая 17-я). Примерки **нет**. `auto_in_prod` false.

**Почему.** Два актива с одним кодом на разных площадках. Тикет на московской 17-й не делает её верной. Create или update здесь — ошибка безопасности, не «почти угадали».

**Руками.** Статус «нужно уточнение». На карточке два кандидата, не один выбранный id.

## S3. Повтор на открытом тикете (бриф, сценарий 3)

Нужно сразу update T-884, без ложного create.

**Вход**

| Поле | Значение |
|------|----------|
| Канал | звонок |
| Отправитель | Андрей, СеверФуд |
| Получено | 2026-08-13T16:40:00+03:00 |
| Текст | Это Андрей из СеверФуда, объект на Дмитровском. Я уже писал минут сорок назад по семнадцатой установке. Сейчас температура 8,3. Резервная камера есть, но мы не уверены, что она выдержит весь товар. |
| Вложение | нет (расшифровка — сам текст) |

**Поиски.** Площадки: СеверФуд + Дмитровское → одна `S-MSK-01`. Активы: ХУ-17 на этой площадке → `A-1001`. Открытые заявки по площадке или активу → T-884. Договор K-101.

**Карточка**

| Слот | Ожидание |
|------|----------|
| Клиент | `resolved` `C-101` |
| Объект | `resolved` `S-MSK-01` |
| Оборудование | `resolved` `A-1001` (из текста «семнадцатая» и/или с тикета) |
| Симптомы | 8,3 |
| Резерв | есть, нагрузка под вопросом |
| История | mention «уже писал», `resolved` `T-884` |
| Договор | `K-101` |

Расчёт ветка `update`. SLA тот же Gold, 60 минут от 16:40 → 17:40. Приоритет не ниже, чем на тикете (`high`). Предупреждение про резерв уместно.

Исход `update`. Примерка **да**, PATCH T-884 (новый summary, приоритет не понижен). `auto_in_prod` true при принятой примерке. Не должно быть POST новой заявки.

**Почему.** Открытый тикет про тот же актив и тот же инцидент. Закрытый бы не оживляли — в сиде T-884 открыт.

**Руками.** Исход «обновить T-884», в журнале разобрано, create-черновика с новым would-id нет.

## S4. Код назвали, в реестре пусто (наш негатив)

В тройке брифа актив либо однозначен, либо находится дважды. Нет случая «написали инвентарный номер, мок вернул ноль». Без этого легко завести заявку на ясную площадку «на всякий случай» — а это мы запретили.

**Вход**

| Поле | Значение |
|------|----------|
| Канал | email |
| Отправитель | Андрей, СеверФуд |
| Получено | 2026-08-13T16:40:00+03:00 |
| Текст | СеверФуд, склад на Дмитровском шоссе, 100. КМ-9 не держит температуру, уже +6. Нужен мастер сегодня. |
| Вложение | нет |

В сиде КМ-9 нет. КМ-4 живёт у Ритейл-Плюс, не здесь.

**Поиски.** Площадка Дмитровское → `S-MSK-01`. Актив `q` / `local_code=КМ-9` → пустой список. Договор можно взять (площадка ясна) — на исход create это не влияет. Тикеты на площадке найдут T-884, но он про A-1001 / ХУ-17, не про КМ-9. Нельзя склеить это письмо с T-884 только потому, что объект тот же.

**Карточка**

| Слот | Ожидание |
|------|----------|
| Клиент | `resolved` `C-101` |
| Объект | `resolved` `S-MSK-01` |
| Оборудование | mention «КМ-9», `not_found`, кандидаты пустые, цитата жива |
| Симптомы | +6 / не держит |
| История | не `resolved` на T-884 |
| Договор | допустим `K-101`, если звали |

Исход `clarify` (или `dispatch`, если поиск актива упал ошибкой — в сиде это просто пусто, значит `clarify`). Вопросы: какой код на самом деле, не ХУ-17 / ХУ-18 ли это. Примерки **нет**. `auto_in_prod` false.

**Почему.** Актив назвали и не нашли. Площадка ясная — недостаточная опора для заявки. Открытый тикет на другой установке того же склада — другой инцидент.

**Руками.** Не «разобрано» с would-id. На слоте оборудования видно «не найдено», не пустое поле как будто кода не было.
